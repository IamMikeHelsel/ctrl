# Counting the work and turning it into useful capabilities

Use four ledgers, not one “percent complete.” Research, proof evidence, callable code and adoption
measure different work. They overlap: one question may yield several proofs and one API; the same
API may have Python, C and ST implementations. Adding those totals would count the same progress
several times.

This snapshot was verified on 22 October 2026 against main-library source, an executed CI log,
the copied runtime inventory and the separate campaign state. The machine-readable companion is
[work-ledger.json](work-ledger.json). Research paths are provenance in the separate checkout, not
missing links or claims that those files ship with main.

The denominator is the frozen roster, not every paper, hypothesis or idea mentioned. The historical
372-family math catalog is a source map, not 372 completed investigations. Three transfer ideas
for one question remain one reviewed question. A failed route can be completed useful research;
its original question can remain open. A later extension supersedes its own next-test plan without
rewriting the history of the initial review.

## 2. Evidence ledger: exactly what was checked?

The main library currently contains **55 `ControlsLean` source modules** and **445 named headline
audit entries**. The full check in [CI run 39790100165](https://github.com/IamMikeHelsel/ctrl/actions/runs/39790100165)
at commit `e4913e69df501b126eab0208582e7db7c671cdfa` reports both “445” audited headline theorems and
“55” checked files. That is actual execution evidence at a named revision, not a promise about
all later commits.

These are useful maintenance counts, not 445 independent ideas, novel theorems or physical
properties. Helpers, equivalent formulations and concrete instantiations may overlap. The research
registry's 223 declaration references likewise do not establish 223 independent proofs or Python
refinement. The repository has **no audited global count of unique mathematical claims or novel
discoveries**; those fields remain unassessed.

Count a mathematical claim by its normalized statement **and assumptions, model, representation
and revision**. Attach multiple receipts for kernel compilation, exact certificates, numerical
checks, simulation and physical measurement. An independent replay increases confidence in the
same claim; it is not a second discovery. A new negative control is a new test, not automatically
a new theorem. Report test cases and semantic mutation classes separately.

## 3. Reusable-consumer ledger: what can someone actually call?

The separate research runtime has **42 domain functions + 4 benchmark entry points + 2 codegen
helpers = 48 registered callables**. It also emits **12 C symbols and 4 Structured Text units**.
The language variants overlap these capabilities; do not add them to obtain “64 features.”
The current main Python package is `erdos_lab`; the research `ctrl.robotics` runtime is not
already delivered by this main package. No Rust implementation was found in that runtime scan.

The count of **release-ready capability packages is unassessed, not zero**. Plenty of functions
work and have evidence, but a released capability also needs an installable supported surface,
input/error contracts, language coverage, target checks, versioning, examples and an owner.
Likewise, “14 catalog families,” “42 numerical functions,” “55 GO routes” and “55 Lean modules”
are different denominators.

Count one capability by a versioned user-facing contract. Python, Rust, C and ST are a coverage
matrix underneath it. For example, a static correction acceptance contract is one capability,
with an offline exact checker and a PLC predicate serving different stages. Its generic proof,
20-case bank, JSON receipt and ST function are evidence/components, not four products.

## 4. Adoption-impact ledger: did it help someone do their job?

Independent external adoption, supported downstream integration count, physical acceptance and
whole-task benefit are **not measured in this audit**. Leave those entries null/unassessed;
do not replace missing measurements with zero adopters, or with positive claims from simulation.
A self-authored example is an integration test, not independent adoption.

Use a matched downstream task as the denominator: the same motion, limits, timing, input data,
hardware and success criteria. Report absolute before/after results, uncertainty and total cost,
including conversion, certificate construction, checking and communication. Multiple improvements
on the same run are not additive gains. For a substantial migration, 30% whole-task improvement
is a useful ambition; a cheap optional adapter can justify less. A newly enabled capability can
pass a separate acceptance gate without any speedup claim.

For example, the executed exact trajectory model in the inventory gives 20 → 3227/195 energy
units (17.26% reduction) under its specified toy parameters. It does **not** clear a 30% migration
bar or demonstrate physical energy savings. Its equation, Python result and C implementation
must not be counted as three independent performance wins.

## A capability receipt connects the ledgers

Give each proposed reusable unit one small receipt, with evidence links rather than adjectives:

| Receipt field | Required contents |
|---|---|
| Question and consumer task | Original question ID, existing workflow, proposed supported action. |
| Invariant/claim | Exact behavior/property, units, frames, numeric semantics and assumptions. |
| Proof | Source theorem/revision/hash, permitted axioms, source-model binding and remaining bridges. |
| Tests | Reproduction commands, independent receipts, boundary/rejection/mutation cases and known failures. |
| APIs and adapters | Current Python/Rust/C/ST entry points separately; caller responsibilities and unsupported modes. |
| Outputs | Versioned schema, error/unknown values, model/context identity and snapshot applicability. |
| Supported targets | Actual tested OS/compiler/runtime/PLC variant; unavailable targets stay unassessed. |
| Benefit | Matched baseline, numerator/denominator, absolute results, uncertainty and integration/runtime costs—or a concrete newly enabled task. |
| Traceability and ownership | Upstream source → frozen claim → implementation commit → build/test receipt → downstream example; maintainer and open obligations. |

A blank template is included in the JSON. An empty field is an outstanding obligation, not a
reason to invent evidence. A release can support a narrow capability while explicitly leaving
broader research questions open.

## Before/after provenance map

**Today:** source question → campaign card/proof/experiment → scattered callable or template →
local demonstration. The artifacts have value; the consumer must recover their assumptions and
integration details manually.

**Packaging target:** source question → versioned capability contract → proof and independent
receipt → supported core API → target adapter → runnable downstream example → measured outcome.
Each arrow has an owner and an acceptance check; a broken arrow remains visible.

For S12, this means uncertain joint model → independently checked support/emptiness certificates →
nonempty safe correction interval → context-bound receipt → selected integer command guard →
actual PLC compiler/scan/application test. The current partial block reaches several earlier
arrows; it does not establish a deployed dynamic safety system. For a downstream optimization
library, retain its optimizer and add an independent consumer at the candidate-output seam rather
than replacing the whole stack. For motion analysis, first offer a matched offline evaluator;
replacing an industrial interpolator requires a separate task/queue/timing contract.

The useful progress report is therefore: **60 reviewed questions; one completed extension;
55 main source modules with 445 executed headline audits at the cited revision; 42 research domain
callables plus six support functions; target and adoption obligations tracked explicitly.**
That states substantial completed work without turning code, proof and impact into one inflated
number.

Assessment quality: A− for accounting scope. Subjective confidence: 95% in these verified counts
and distinctions; not a calibrated probability of novelty, release readiness or physical success.
