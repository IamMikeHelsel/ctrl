# R03 source and primary-source scope

The18October addendum is expressly a proposal, with no implementation or new proof. Its ordering inequality is sufficient only under truthful time bounds and a defined mapping to a physical clock. It separates timing, retained-history binding and progress.

The actual `overnight-reviewer-bundle-v4/src/FutureCommit.lean` already compares complete Base and Task records, not version integers alone. Base includes events, offset, width and version. Task includes goal, request, deadline, speed, acceleration, jerk limit and version. `commitOK` assumes one atomic read of all predicates and the ideal clock; `committed_base_invalidates_pending` derives invalidation from the incremented natural-number version. No frame/calibration identifiers, machine memory model, atomic instruction, actuator queue or physical clock implementation are supplied by this theorem. Those are extension obligations, not discovered source bugs.

[Herlihy–Wing1990, author-hosted PDF](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf) defines linearizability through an abstract operation taking effect between invocation and response. This supports specifying an atomic composite commit operation; separately atomic reads and writes do not automatically implement that composite specification. Abstract atomicity is not a bound on runtime duration or physical actuation.

[Corbett et al., Spanner2012, publisher PDF](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf), §3 and§4.1.2, exposes an interval containing the absolute time at a time-query invocation, and uses commit-wait within a larger transactional protocol. That interval is not automatically a bound for a later compare-and-swap. Timestamp/interval ordering does not replace read-set validation, locking or atomic state transition. Only the indicated sections and relevant source definitions were inspected; no full system audit or robotics applicability claim follows. Initial Google-hosted PDF redirects failed; publisher PDF succeeded.

The official [Spanner external-consistency documentation](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency) independently distinguishes consistency of a transaction from isolated object operations. This is prior art and motivation; a local robotic executor should not acquire a database merely to implement the abstract contract.
