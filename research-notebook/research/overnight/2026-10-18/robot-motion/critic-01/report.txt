Accepted result

For a finite rational event history, the Boolean acceleration guard is exactly
equivalent to positive filter width, a nonnegative limit, and the acceleration
limit at every future real time. The acceleration is the second derivative of
the same retained four-box position reference. The proof does not assume the
desired bound and does not depend on sampled numerical results.

The all-pairs list contains every needed stationary point. It may contain roots
from nonadjacent knot pairs, including roots outside those pairs. Such extra
points remain at or after the current time. They therefore cannot invalidate
the equivalence. The proof separately covers the final zero tail, coincident
knots, the cell cut by current time, constant nonzero jerk, and zero jerk with
nonzero constant acceleration. It does not divide by a zero jerk difference.
The rational-to-real bridge applies to the same primitive and event list.

The finite selector accepts the first supplied execution time that meets its
checks. The selected new event is not before the supplied ready time. Every
retained event, including a queued future event, must finish by the deadline.
The reference prefix through the selected execution time is unchanged. The
final position is the initial offset plus the sum of every retained increment.
The caller must encode the desired goal as that sum. No intent inference is
present in the theorem.

The old failed case remains unchanged: return execution at 0.52 s, acceleration
-21/32 m/s^2 at 0.77 s, and rejection of the 0.5 m/s^2 limit. The new case executes
the return at 0.62 s. It has separate all-time reference velocity, acceleration
and jerk bounds, and exact reference rest by 1.42 s. The deadline remains 1.70 s.
The source, report and figure distinguish these cases. The delayed reference
travels farther toward the old goal. It is not an emergency-stop or travel-limit
result.

Boundary challenges

The generic selector has no velocity test. A separate witness admits a reference
that exceeds an arbitrary 0.5 m/s velocity limit. The new equal-and-opposite
two-event example has its own velocity proof; that proof does not generalize
the selector to arbitrary histories.

An empty candidate list returns none even when the concrete 0.62 s candidate
passes. Thus none rejects only the supplied list. It is not a continuous-search
completeness result or a proof of trajectory infeasibility.

The full-event deadline rule is conservative even beyond finite search. A
retained zero-amplitude event at 10 s rejects a deadline-4 candidate although
the event has no effect on the reference. This is consistent with the stated
rule. Do not describe the deadline test as necessary for all feasible motion.

Readiness is an input to the theorem. Computation time, packet timestamps,
transport, clock error and actual dispatch are not proved to satisfy that input.
The reference result bounds no physical velocity, acceleration, torque, contact,
Franka firmware behavior, or physical settling. Existing plant theorems need
explicit composition from the original state; do not reset state at the delay.

Next gates, in order

1. Compose this already velocity/acceleration/jerk-proved return with the actual
   scalar plant from its original state. Freeze a new comparison protocol and
   allow strong baselines to succeed. Measure physical task completion, waiting,
   tracking error, actual jerk, rejection and extra forward travel. Keep old
   failed cases intact. This tests practical value sooner than adding guards.
2. In parallel, prove an adjacent-cell implementation equivalent to the exact
   acceleration contract. Deduplicate/sort knots with a checked implementation,
   cache endpoint values, and benchmark against the same declared inputs.
3. For arbitrary histories, a cubic Bernstein velocity bound is a tractable
   sufficient guard. On a cell of length dt, prove the four control values are
   vL, vL + dt*aL/3, vR - dt*aR/3 and vR. Bounding all four can imply a velocity
   bound. It must not be called exact or necessary. It still does not construct
   a feasible task response or establish an improved robot controller.
